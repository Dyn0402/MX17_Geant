## Task 1 — V6: expose the 100 µm inter-pad gaps

**What's assumed today (W1, plan §3, `design/RESPONSE_SIM_PLAN.md:435`):** buried trace layers
under the pads are screened by the segmented pad plane and ignored, because the solver treats
the pad plane as a full Dirichlet pattern. The pads are 680 µm on a 780 µm pitch, so there's a
100 µm gap between them where nothing actually shields what's underneath. The plan's own
estimate: this should shift the comb Green's functions G_n by "a few %" (`plan:545`). Nobody has
run it.

**Where the physics lives:** `response/solver/wpot.py` (the semi-spectral solver — read its
docstring, it derives C(k)/S(k) from the layer stack) and `response/solver/kernels.py` (comb
assembly from the per-phase solves). The pad plane boundary condition is what needs to change:
in the gap, don't clamp to the pad Dirichlet value — let it see whatever's actually below
(floating / open, absent a modeled trace-layer geometry; check `response/common/` for whether a
trace-layer pattern is already parsed from the header before assuming there isn't one).

**How to structure it:** `response/solver/v5_mesh_ripple.py` is the template for exactly this
kind of check — a self-contained, self-documenting "is assumption X safe" script with a
docstring that states the assumption, why it might not hold, and what's out of scope. Write
`v6_...` the same way rather than folding it into `wpot.py` directly.

**Acceptance:** reproduce the plan's own expectation (G_n shift is percent-level, not order-1);
re-verify the closed-form sum rule still holds (~5e-7, same bar S1 already passes — see
`test_charge_audit.py` / `test_lut_vs_solver.py` in `response/digitizer/` for the pattern). Record
the result in `design/RESPONSE_SIM_PLAN.md` T5 row (currently says "V6 ... still not run").

## Task 2 — T10 slow path: the ion's lateral shape

**The open approximation (P3, plan §0a):** ions carry 90.8% of the induced charge, and they
currently get the *surface* kernel's lateral shape (the narrowest possible) for their entire
transit from z=0 to z=g, because S1 only solved the z=0 plane. The real weighting field widens
with height — this is the last known physics approximation in the digitizer chain, and T10's own
certification (`test_lut_vs_solver.py`) explicitly says it certifies caching fidelity only, not
this.

**The spec, verbatim from the plan (`design/RESPONSE_SIM_PLAN.md:659-660`, §3 point 6):**
build response templates `R_n(x0 mod 31.2 mm, t)` — the full current on channel n for a standard
avalanche at (x0,y0) — via Garfield++ `Sensor` + `ComponentGrid` loading the **S1 Ψ time slices**
(`LoadWeightingField(file, fmt, t_k, true)` per slice; `SetDelayedSignalTimes`;
`EnableDelayedSignal(true)`; `SetWeightingFieldOffset` to place channels). Trajectories are
*parameterized* (electron spike + ion line current), **not microscopic per event** — this does
NOT need real avalanche microphysics, so it is not blocked on T7. Run O(100) events per parameter
point; acceptance is <2% waveform residual against the fast-path LUT, matching the bar
`test_lut_vs_solver.py` already uses for the z=0 caching check.

**Inputs:** the S1 Ψ volumetric grid, `wpot_<ch>_<params>.npz` (file contract in plan §2) —
axes `x,y,z,t` with 8–16 z-slices to the mesh, from the production kapton+glue grid
